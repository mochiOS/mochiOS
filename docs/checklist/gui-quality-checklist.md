# GUI品質の内部チェックリスト

デスクトップと標準アプリの見た目、操作、作業の完了、快適さを手動で確認します。
ViewKitの部品テストと[統合テスト](../testing.md)を継続し、GUIの確認結果をリリース判断へ対応付けます。
繰り返し再発し、手順と期待結果が安定した操作は、自動試験へ追加する候補として記録します。

対象範囲と出荷条件は[Kinako完成チェックリスト](mochios-27-kinako-checklist.md)に従います。
本書は第6・7・11節などの手動確認を具体化するもので、将来機能を新たな必須条件に加えません。

## 確認の進め方

1. 本書を対象ビルドごとの確認記録へコピーし、下の環境欄を埋めます。
2. まずEditの保存、FilesからViewerでの画像表示、権限確認を一通り行います。
3. 採用している部品と標準アプリへ確認範囲を広げ、項目ごとに実際の結果を記録します。
4. 不具合をIssueへ関連付け、修正後は同じ手順と、影響する共通部品の利用箇所を再確認します。

チェックは、記録したビルドと条件で合格を確認してから付けます。初期状態はすべて未検証です。
結果には「未検証・検証中・合格・不合格・対象外・判定待ち」を使います。
対象外には理由を付け、仕様や数値基準が未確定なら判定待ちとして残します。

## ビルドと確認環境

| 記録項目 | 記入内容 |
| :-- | :-- |
| 確認者と日時 | 担当者、確認日。 |
| ビルド | OSの版・build・commit、MWS snapshot、配布イメージのSHA-256、確認するアプリの版。 |
| 環境 | 実機またはKVM、CPU、RAM、GPU、描画経路。KVMではQEMUの版と起動条件も記録します。 |
| 表示 | 解像度、表示倍率、リフレッシュレート、ディスプレイ構成、Light/Dark。 |
| 入力 | 表示言語、キーボード配列、マウス等の機器、IMEの状態。 |
| 開始状態 | OS起動後初回かアプリ再起動後か、ユーザー、設定、開いているウィンドウ。 |
| 確認用データ | ファイル、保存先、権限、ネットワーク等の前提。破棄できる確認用データを使います。 |
| 証拠の保持先 | 記録、画像、動画、ログ、自動試験結果の所在。リリース判定時にも参照できる場所を残します。 |

言語・テーマ・倍率等を変えた結果は、どの条件で確認したかを項目ごとに追えるようにします。
自動試験の成功から、手動確認の欄を合格に変更しません。

## レビューの判定

操作不能、データ消失・誤保存、権限の誤承認等があれば、該当項目を不合格として記録します。
見た目の問題、未検証、対象外、判定待ちも残し、チェック済みの件数だけで全体を合格にしません。
最終判断はKinako完成チェックリスト第21節へ、対象ビルドと確認範囲を付けて引き継ぎます。

| 判定項目 | 記入内容 |
| :-- | :-- |
| 全体の判定 | 未検証。 |
| 確認範囲 | 確認したアプリ、GUI項目ID、環境の組合せ。 |
| 残る問題 | 未解決Issue、未検証・対象外・判定待ちの項目と理由。 |
| 再確認 | 修正後に確認する範囲と、その結果。 |
| レビュー担当と日時 | 判定を行った担当者、日時、記録の保持先。 |

## レンダリング品質の回帰確認

2026-11-15の共通描画修正では、次の責務を各所有リポジトリに配置しています。
外観の合格は下記の実機確認後に記録します。ビルド成功だけで合格にしません。

| 対象 | 実装した対策 | 自動確認／追加の実機確認 |
| --- | --- | --- |
| GPUからCPUへの切替 | 新規CPUバッファは全面再描画し、GPUの更新領域を継承しない | 初回・保持済みバッファの更新範囲テスト。GPUフォールバック後の画面欠けを実機確認 |
| プレビューと実機の差 | 物理／論理解像度、スケール、アトラス、頂点上限、合成方式を診断出力 | Linuxは `VIEWKIT_RENDERER_DIAGNOSTICS=1 mmake ui`。mochiOSはViewKitのperfログを照合 |
| ウィンドウのDPI | 角丸・枠線・影・移動時の更新範囲を同じ倍率にする | 75／100／125／150／200%の寸法テスト。各倍率で移動・リサイズ・最大化を実機確認 |
| 細線とクリップ | 分数座標の矩形カバレッジと、MSAAに依存しない角丸クリップのAA | ピクセル面積、退化三角形、頂点上限、内部の不透明度、UVの保持を検査 |
| 画像補間 | 物理サイズでのCatmull–Rom準備処理、Nearestの専用サンプラー、上限付きキャッシュ | 補間差・透明色・キャッシュ再利用。縮小画像とピクセルアートを実機比較 |
| 文字 | CPU／GPUで共通の原点・ベースラインの丸め規則を使う | 英日混在、異なる文字サイズ、既存の400／500／600ウェイトと入力欄のテスト。小さい文字は実機でも比較 |
| 共通部品の配置 | FirstBaselineと共通RowDensityを追加し、Sidebarの選択面も共通半径にする | ラベル・入力欄・型消去・余白・スタックの伝播、折返しと大きな文字の計測 |
| デスクトップのコントラスト | Dockとステータスの前景を実際の背景サンプルから選ぶ | 単色背景のコントラストを検査。模様の強い壁紙や背後のウィンドウは実機確認 |
| アプリアイコン | 表示サイズ×DPIでSVG／画像を準備し、Dock・一覧・検索・通知の共通マスクを使う | DPI別サイズ、上限、再利用を検査。通知とDockの輪郭を実機比較 |
| 影と色の整合 | 共通の滑らかな減衰とsource-overの濃度補正、premultiplied RGBA8の共通合成 | 減衰、濃度、透過境界、合成テスト。淡い影の段差は出力ディスプレイでも確認 |

色の契約は現在のencoded UNORMであり、linear-light／ICC／HDR対応を意味しません。
アトラスだけをsRGBへ変更することは禁止します。頂点色・テクスチャ・合成先を
一緒に変更して比較できる段階で、別の色管理対応として扱います。

Linuxの外部画像テクスチャ、4×MSAAの利用可否と、mochiOSの1024×512アトラス／
65,536頂点の上限は同一ではありません。mochiOSで収まらない画像は正しいCPU描画に
切り替えます。この修正はネイティブの大画像テクスチャ対応を実装したものではありません。

最低限、同じ壁紙と画面構成で、静止画、ウィンドウの重なり、DPI変更、細線、
透過アイコン、文字のベースラインを比較してください。画面キャプチャの縮小画像だけで
小さい文字や1物理ピクセルの線を評価せず、原寸画像と実ディスプレイの両方を用います。

### CPU計測と開発ビルド

境界と交差する三角形5,000回の計測では、共通幾何も最適化したプレビュー条件で、
旧hard clipが約10.1ms、cached AAが約35.7msでした（約2.0／7.1µs/回）。
この例のAA出力は22三角形、キャッシュは14,464バイト、初回生成は約0.50msです。
境界の追加カバレッジには計算量が増えます。内部領域は別の一定時間の高速判定を使います。
これはCPUの局所計測であり、実機のフレーム時間やGPU性能の測定結果ではありません。

プレビューではViewKitと共通幾何を最適化し、アプリの差分コンパイルは維持します。
AppCoreは生成されたプレビュー用manifestでRustのrlibだけを生成します。
SDK用の元manifestにあるstaticlib／cdylibの配布設定は変更しません。
テストと通常起動は同じ同梱フォントディレクトリを使います。

### Settingsの整列と密度

### Applicationsのページ移動と起動表示

DockのApplicationsは、ページ間を共通のSpringAnimationで追従させます。
逆方向への入力では表示中の位置と速度を引き継ぎます。検索や開き直しは先頭へ
リセットし、ページ数が複数ある間はパネル寸法を固定します。描画とクリック判定は
表示中のページ位置を使い、グリッド領域外へ移動したアイコンは操作対象にしません。
共通の動きを抑えた設定では即時切り替えになります。

新規ウィンドウは、最初の有効な内容を受け取ってから短くフェードします。
共通の純粋なタイムラインはviewkit-gpu-protocolのwindow_motionに置き、
現在の標準値は180msです。LinuxプレビューはBinder、実機の合成はKagamiが所有します。
BinderはKagami所有のウィンドウを二重に描画しません。レイアウト・入力座標は固定し、
最小化からの復帰やフォーカス変更では起動フェードを再生しません。
Kagamiの保護されたpresentationは即時表示です。

KagamiのGPU経路はキャッシュした形状を維持し、合成時のpremultiplied RGBAを
同じ比率で減衰させます。CPU経路も内容・輪郭・影のcoverageを同じ不透明度にします。
フェード中のウィンドウの範囲だけを更新し、終了後の定期ポーリングは行いません。

アプリアイコン未指定・欠落・破損は、Binder自身の既存appicon.svgへフォールバックします。
Dock・Applications・検索・アプリ切り替え・通知でapp_iconの共通描画を参照します。
