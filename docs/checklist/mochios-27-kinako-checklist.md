# mochiOS 27 Kinako 完成チェックリスト

## 判定の前提

最終目標はmacOS, Windowsと競合できる製品OSです。Kinakoでは、日常の事務作業を行い、その同じ環境でプログラミングを学び、アプリの作成・デバッグ・公開まで進められるデスクトップ体験を重視します。

品質上の優先順位は、安定性、UI/UX、セキュリティ、アプリ環境、パフォーマンスです。順位が低い項目も、確定した合格条件を満たす必要があります。

本書では、利用者が確定した範囲を「確定要件」、その範囲を確かめるための具体的な確認項目を「検証条件」として扱います。検証条件はこのチェックリストでの具体化であり、個別の実装方式まで承認済みという意味ではありません。

チェックは「コードが存在する」ではなく、対象ビルドで期待する結果を確認できた時点で付けます。空欄は未実装を意味せず、未検証です。適用しない項目は理由を記録して対象外とし、将来機能を未完了項目として数えません。

標準アプリの機能範囲は資料[A]を参照します。ただし、会話で後から決まった条件を優先します。資料[A]のFilesに含まれる日常利用向け外部ストレージ対応は、今回は必須から外します。

## 1. 対象範囲

### Kinakoの確定要件

一般的なx86_64 PCを対象とします。必要なCPU仮想化機能とIOMMUを利用できる比較的新しい構成を想定し、GPU性能の目安は内蔵Intel Xe程度です。特定のCPU・GPU型番すべての動作保証を、この表現だけから導きません。

RAM 1GBで書類作成・ブラウジングができることを目指します。表示は16:9を想定し、1920×1080を基準解像度候補として記載します。解像度の数値は利用者による明示確定前です。

mDriverを通じてLinuxの物理ドライバ資産を利用します。アプリ配布はAppStore、ダウンロードしたmpkg、CLIパッケージマネージャーの3経路です。既定のファイルシステムとしてext4を利用できるようにします。

### Kinakoの必須に含めない範囲

- aarch64正式対応、ノートPCの完全対応、Linux Application VM。
- 独自の次世代ファイルシステム、ディスク全体暗号化、一般PCへのSecure Boot正式対応。Secure BootはmochiPC向けです。
- VPN、プリンタ、日常利用向け外部ストレージ、バックアップ機能、専用移行ツール。
- 終了前の作業状態の復元、独自IDE、独自の事務作業用アプリ。
- OSログインへのmochiOS ID統合、クラウド同期型のパスワード保管。
- 画面を見ずに全工程を完結できるというアクセシビリティ保証。

インストール・Recovery用USBと、オフライン再インストールは対象です。「外部ストレージは対象外」を理由に、これらを除外しません。AppStore内での認証要否は、OSログインへのID統合とは別です。

- [ ] HW-02：インストール先、消去される領域、作成するユーザーを確認でき、誤ったディスクを無確認で消去しません。

- [ ] HW-04：実機のGPU、ストレージ、入力、ネットワークをmDriver経由で利用し、mochiOSの利用者向け機能まで一連の動作を確認します。
- [ ] HW-05：対応機器の接続・切断・再接続で、機器一覧と利用状態が一致します。USBの確認対象は今回の対応範囲に限ります。
- [ ] HW-06：mDriverの障害・再起動時に、古い共有資源や接続を誤って再利用しません。無停止復旧できない機器まで、復旧可能とは表示しません。
- [ ] HW-07：安全な再起動が必要な障害と、機能単位で復旧できる障害を区別し、再試行でデータ破損を広げません。

## 4. 基本OS・データの整合性

特定のスケジューラ、メモリ管理方式、Copy-on-Write等の採用そのものは、本書の一律必須条件にしません。

- [ ] CORE-01：アプリやスレッドを反復して起動・終了しても、不要なプロセス、メモリ、ハンドル、IPC資源が継続的に残りません。
- [ ] CORE-02：複数アプリの同時実行で、他アプリのメモリや資源へ権限外アクセスできません。
- [ ] CORE-03：メモリ不足・容量不足・I/Oエラーを検出し、成功していない保存や処理を成功と表示しません。
- [ ] CORE-04：アプリ停止、サービス停止、デバイス異常を区別し、影響のない処理まで不必要に停止させません。
- [ ] FS-01：ext4の対応機能を定義し、その範囲でファイル・ディレクトリの作成、読み書き、移動、名前変更、削除を確認します。
- [ ] FS-02：未対応のファイルシステム機能を検出した場合、安全に拒否するなど、破損を生む処理を避けます。
- [ ] FS-03：保存完了として扱う条件と永続化の関係を定義し、正常保存後の再起動で内容が保持されます。
- [ ] FS-04：既存ファイルの更新中に障害が起きても、成功していない更新を完了済みと扱わず、復旧後の状態を確認できます。
- [ ] FS-05：異常終了後に整合性を確認・修復でき、修復不能な場合はその事実を表示します。
- [ ] FS-06：ユーザー間のファイルアクセス制御を、GUI・CLI・アプリAPIの各経路で迂回できません。
- [ ] FS-07：日付・時刻・タイムゾーン変更後も、ファイル表示、予定、証明書検証などに使う時刻の扱いが矛盾しません。

## 5. 性能の完成条件

確定した時間目標は、再起動後の最初のアプリ起動にも適用します。二回目以降だけの測定で合格としません。

| 指標 | 確定した目標・判定範囲 |
| :-- | :-- |
| OS起動 | mBootの起動開始からログイン画面の表示まで8秒以下です。 |
| 標準アプリ起動 | Terra以外は、起動操作からアプリを操作可能になるまで200ms以下です。 |
| Terra起動 | 起動操作からタブ操作が可能になるまで500ms以下です。外部Webページの読み込み完了は含めません。 |
| 基本描画 | 60Hzを基本とします。 |
| 高リフレッシュレート | 対応環境で120Hzを利用できます。常時120fps維持や、全高負荷条件での120fpsは要求しません。 |
| 1GB RAM | 書類作成とブラウジングが可能です。無制限のタブ数や、Zoomを含む全作業の同時実行までを意味しません。 |
| アイドルRAM | 512MBを目標にしますが、これ単独の厳密な上限で不合格にはしません。 |
| ログイン後 | デスクトップ表示後に追加の待機操作を要求せず、入力を受け付けます。 |

- [ ] PERF-01：mBoot開始時刻とログイン画面表示時刻を同一の測定で記録し、8秒以下です。ファームウェアがmBootを起動する前の時間とは分けます。
- [ ] PERF-02：各標準アプリの再起動後初回起動を測定し、Terra以外は200ms以下で操作可能です。空のウィンドウだけの表示は完了と数えません。
- [ ] PERF-03：Terraの再起動後初回起動で、500ms以内にタブを操作できます。Webサイトの読み込み時間は別に記録します。
- [ ] PERF-04：ログイン後、最初のクリックやキー入力を取りこぼさず処理できます。
- [ ] PERF-05：60Hz環境で、ウィンドウ移動、スクロール、メニュー、標準アプリのアニメーションを確認し、フレーム間隔と引っ掛かりを記録します。
- [ ] PERF-06：120Hz対応環境で、表示設定だけでなく実際の描画更新も120Hzに対応することを確認します。
- [ ] PERF-07：RAM 1GBの構成で代表的な文書編集・ブラウジングを完了し、メモリ不足による操作不能や作業の喪失がないことを確認します。
- [ ] PERF-08：アイドル使用量を、mBoot・mDriver・mochiOS・標準常駐処理を含む全体と内訳で記録します。共有メモリの二重計上、キャッシュ、予約領域の扱いを明記します。
- [ ] PERF-09：性能結果にはPC構成、ビルド、画面条件、測定回数、起動前状態、各測定値を残します。平均値だけで目標超過を隠しません。

60Hzで許容するフレーム欠落率、入力遅延の上限、性能試験の反復回数は未確定です。計測を行うことと、未確定の数値基準に合格したとすることは区別します。MB・GB表記は利用者の指定を保持し、試験設定では実際のバイト数も併記します。

## 8. OS共通WebView・ブラウザエンジン層

確定要件：ViewKitに差し替え可能なエンジン層を設け、初期バックエンドをWebKitとします。エンジン本体はOS共通配置です。第二エンジンの製品搭載や実行中の切り替えは、Kinakoの必須条件には追加しません。

- [ ] WEB-01：アプリはViewKit側の公開WebView APIを使い、エンジン内部へ直接依存しなくても通常の埋め込み操作を行えます。
- [ ] WEB-02：エンジン本体を各アプリへ静的リンクで重複同梱せず、OS側の共通実装を利用します。
- [ ] WEB-03：薄いアプリ側連携部分とエンジン本体を区別し、共有配置を実現するために全Webコンテンツを同一実行環境へ集約する必要はありません。
- [ ] WEB-04：ユーザー・アプリ・一時利用状態のCookieや保存領域を分離し、明示していない共有が起きません。
- [ ] WEB-05：Webコンテンツの停止やクラッシュが、無関係なアプリやOS全体の停止に直結しません。
- [ ] WEB-06：カメラ、マイク、画面共有、ファイル取得、クリップボード等のアクセスで、OSのCapabilityと許可UIを迂回できません。
- [ ] WEB-07：Webサイトの権限と、埋め込み元アプリの権限を区別し、どの主体に許可したかを確認できます。
- [ ] WEB-08：エンジン層の機能差・非対応操作・エラーを呼び出し元へ返し、未対応なのに成功扱いしません。
- [ ] WEB-09：共通WebViewの更新後にTerraと埋め込みアプリの代表操作を再試験し、バージョン不整合時は原因を表示します。

- [ ] TERRA-02：閲覧履歴・ブックマーク・ダウンロードなど、採用する基本機能がユーザーごとに保存・管理されます。
- [ ] TERRA-03：Wordのブラウザ版とGoogle スプレッドシートで、サインイン、日本語入力、編集、保存、再表示を確認します。
- [ ] TERRA-04：Webへのファイル添付・アップロードと、ダウンロードしたファイルの標準アプリ連携を確認します。
- [ ] TERRA-05：Zoomで音声・カメラを利用でき、画面共有対象の選択と開始・停止を確認します。
- [ ] TERRA-06：画面共有・録音・撮影中であることを把握でき、許可撤回後の新しいアクセスや共有継続を適切に止められます。
- [ ] TERRA-07：切断・再接続、期限切れセッション、証明書エラーを区別し、通信失敗時に保存完了等を誤表示しません。

## 10. ローカルキーチェーン・Terraのパスワード管理

確定要件：keychain.service相当のOS基盤へ完全ローカルに保管し、Terraからパスワードマネージャーとして扱えます。ディスク全体暗号化の対象外指定とは分けます。

次の機能は、パスワードマネージャーとしての受け入れ確認へ具体化したものです。自動解錠や再認証の細かな方式までは確定していません。

- [ ] KEY-01：TerraからWebサイトの資格情報を保存し、既存項目の更新を確認できます。
- [ ] KEY-02：保存済み項目の一覧、編集、削除をTerraから行えます。
- [ ] KEY-03：対応するWebサイトへ保存済み資格情報を入力できます。別サイトや別ユーザーへ誤って入力しません。
- [ ] KEY-04：複数の保存アカウントを区別し、対象サイトと利用する項目を確認できます。
- [ ] KEY-05：保管庫の秘密情報を平文のまま永続化せず、復号用の秘密を同じデータと無保護で並べません。
- [ ] KEY-06：アプリ名やBundle IDを名乗るだけでは他アプリの秘密情報を取得できず、ユーザー境界も越えられません。
- [ ] KEY-07：保管庫が施錠・利用不可・アクセス拒否の状態では秘密情報を返さず、アプリ側に適切な失敗を返します。
- [ ] KEY-08：保存・利用・管理をOSアカウントのローカル機能で行い、保管庫のクラウド同期やmochiOS IDログインを前提にしません。
- [ ] KEY-09：パスワード、復号鍵、認証トークンが通常ログや診断送信へ流出しません。
- [ ] KEY-10：ユーザー切り替え、ログアウト、サービス再起動、保管庫更新の失敗で、別ユーザーの秘密が利用可能になりません。

次の項目は機能実装の有無ではなく、仕様または検証基準が未確定です。確定済みの上位方針を変更せず、詳細が決まった時点で対応する試験へ反映します。
