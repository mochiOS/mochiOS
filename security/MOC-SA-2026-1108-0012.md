# MOC-SA-2026-1108-0012

| 項目 | 内容 |
| :-- | :-- |
| タイトル | POSIXのパス操作でアプリのfilesystem Capabilityが強制されない |
| 状態 | 修正実装済み・動作未検証 |
| 深刻度 | High |
| 影響を受けるコンポーネント | posix.service・アプリ起動時のnamespace委譲 |
| 確認したバージョン | services `a2c9b3a69967fdc611a75994ca4f1a3f9fc926e6` |
| 修正済みバージョン | Fix MOC-SA-2026-1108-0012（未リリース） |
| クレジット | 内部監査 |

## 概要と根拠

アプリごとの`fs.read.user.*`、`fs.write.user.*`等を宣言・付与していても、
POSIXのパス解決経路では、それらの有無や対応するnamespaceの縮小を検査していません。

- `services/capability/src/native_app.rs`はアプリにPOSIX control endpointを継承させます。
- `services/posix/src/open_request.rs`は`prepare_open_at`から`path_request::with_paths`へ進みます。
- `services/posix/src/lib.rs`の`prepare_open_at`はoptions・添付数を検査し、UID/GIDを取り出しますが、パスのCapabilityを検査しません。unlink、rename、mkdir等も同様です。
- `services/posix/src/path_request.rs`はサービス所有のroot/cwdを使います。初回は`open_session_root`で作成します。
- `services/posix/src/main.rs`の`open_session_root`は対象UID/GIDで`/`を開きます。アプリの宣言に応じたrootの縮小はありません。

## 成立条件と影響

POSIX control endpointと登録済みのPOSIX sessionを持つアプリが対象です。
ファイル権限を宣言・承認されていなくても、POSIXのopenやmutation要求を直接送ることで、
同じUIDのmode bitsで許される範囲を読み書きできます。
書類等のフォルダー別同意や、アプリ単位でfilesystem権限を与えない判断が実効性を失います。

filesystem.serviceのUID/GID検査、immutable System、添付Handleのrights検査が
無効になっているという報告ではありません。他UIDの保護されたファイルへ無条件に到達できるとは判断していません。
ユーザーが明示委譲したFileHandleの操作も、新規パス探索とは別の正当な経路です。

## 修正方針・緩和策

POSIX brokerが新しくパスからauthorityを作る時点で、カーネル由来の送信元と
その実行imageに結び付いた許可を確認し、ユーザーランドで許可namespaceを強制します。
あるいは起動時に縮小したdirectory Handleだけを委譲し、そこからの探索に限定します。
libc内の検査だけでは直接IPCで迂回されるため不十分です。
既に明示委譲されたFileHandleの権限は独立に尊重し、カーネルにパスやサービス方針を追加しません。

修正までは、manifestだけでファイルアクセスを隔離できるとは扱わないでください。
受信からfilesystem要求の生成までを静的に確認しました。試験追加・実行、実ファイルへのアクセス実証、ビルドは行っていません。

## 実装した修正

`Fix MOC-SA-2026-1108-0012`で、POSIXがカーネル由来の送信元のfilesystem権限を取得し、controller専用のfilesystem要求にnamespace policyを付けるようにしました。FDのread/write等にはこのパス用処理を追加していません。

filesystemはserialized namespace操作の中でsymlink解決後の対象を再構成し、read・mutationを別々に検査します。open、作成、unlink、renameの両側、hardlink、symlink、stat/access、属性変更、timestamp、FIFO、UNIX socket、パス照会を対象にしています。独立したcanonicalize RPC後の再openにはしていません。

- `fs.*.user`は`/home`直下のホームの実際のUID所有権と、既存のユーザー別アプリ保存領域に対応します。環境変数USER/HOMEは認可に使いません。
- Documents等の個別許可は、対象ホーム配下の該当フォルダーに限定します。外部を指すsymlinkは許可範囲を拡張しません。
- Systemの公開読み取りとnull等の標準デバイスは、既存のmode bits／device権限を保った上で扱います。privateなroot/cwd用search参照を、読み取り可能なdirectoryとしてアプリへ渡しません。
- 明示添付された読み取りdirectoryは、その実体の配下だけを読めます。読み取り参照からmutation権限を作らず、通常のcwdを明示委譲と誤認しません。既存FileHandleの操作は独立に維持します。
- read scopeは作成元のnamespace policyを保持し、代理側の広い権限を使いません。socket workerへの内部要求も元のpolicyを保持します。

POSIXとfilesystemのmochiOSターゲットでコンパイル確認済みです。試験追加・実行、KVM動作確認は行っていません。既存の標準ホーム配置以外へのホーム移設は、この変更で新たに対応するものではありません。
