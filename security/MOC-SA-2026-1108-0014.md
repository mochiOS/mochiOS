| タイトル | 一般セッションのSettingsから管理者認証なしでアカウントを変更可能 |
| 状態 | 修正実装済み・動作未検証 |
| 深刻度 | High |
| 影響を受けるコンポーネント | Settings.app・user.service・capability.service・secure-ui・Terminal・sudo |
| 確認したバージョン | services `a2c9b3a69967fdc611a75994ca4f1a3f9fc926e6`、settings `f272a46b4739911d58334d1cf6a2c66726e7abfa` |

## 概要と根拠

Settingsのmanifestは`account.other.modify`を要求します。通常のアプリ起動時にこのシステム権限を
付与する一方、実際の利用者について管理者の認可を確認する経路がありません。
`applications/settings/src/main.rs`のChangeとDelete Userは、旧パスワードや管理者認証を要求せず
選択したアカウントに対して`accounts::set_password`／`accounts::remove`を呼びます。

`services/user/src/main.rs`の受信側も、送信元の`account.other.modify`だけで
AddUser／RemoveUser／SetPasswordを許可します。操作する人の権限、対象との関係、
操作に結び付いた管理者認証の証跡を検査しません。
アプリが正規のSettingsであることと、その操作を行う人が管理者であることが混同されています。

## 成立条件と影響

一般ログインセッションから正規のSettingsを起動できる構成が対象です。
他の非rootユーザーを認証なしでアカウントDBから削除できます。
パスワード変更では新しいhashを設定してlockedも解除します。

パスワード変更の成立にはkeychain側の追加条件があります。
`services/keychain/src/login_session.rs`の`PrepareLoginPassword`は、vaultがない対象では成功しますが、
既存vaultがある場合は対象が現在のログインユーザーで、vaultが解錠済みであることを要求します。
したがって任意の既存vaultを持つ他ユーザーのパスワードを必ず変更できる、またはvaultを解読できる、
という主張ではありません。root削除もUserDatabaseが拒否します。

## 実装した修正

`Fix MOC-SA-2026-1108-0014`で、既存UIがAdministratorとして扱うUID 0の方針を、受信側でも強制しました。

- AddUser／RemoveUser／SetPasswordは`account.other.modify`に加えて、POSIXが管理するreal/effective UIDの両方が0であることを要求します。送信元endpointから取得したnative ProcessHandleを添付して照会し、要求内のUIDやパス・環境変数は使いません。
- 照会の前後で同じProcess object・image・native identityであることを確認します。正規Settingsやuseraddのimageにprivileged capabilityがあるだけでは、一般ログイン利用者を管理者として扱いません。
- 当初はSettingsの管理操作をUID 0セッションに制限しました。継続修正では、一般セッションからも以下の共通管理者認証を通して実行できるようにしました。直接RPCの受信側での制限は維持します。
- 自動ログイン設定のディレクトリをroot所有・0755にし、既存インストールもuser.serviceのready前に保護します。非root所有・symlink・書き込み可能な旧設定は安全な無効設定へ置換します。secure-uiもファイルと親の所有権・modeを確認し、不適切な設定では自動ログインしません。
- アカウント一覧のSnapshotにはpassword hashを含めません。POSIX向け公開照会を独立した読み取り専用endpointへ委譲し、更新側がPOSIXへ問い合わせる間の相互待ちを避けます。

同じIDの継続修正として、GUIとmshから使う管理者認証を共通化しました。

- 最初の一般ユーザーを永続化された`admin`グループへ登録します。既存環境ではグループが未作成の場合だけ、最小UIDの一般ユーザーを一度登録します。既存の空グループは再設定しません。削除時に所属を取り除き、同名の再作成へ引き継ぎません。
- パスワードとグループの検証はuser.serviceだけが行います。呼び出せるのはnative Process・image・system identityと`capabilities.manage`を検証したcapability.serviceです。5回の失敗で30秒間制限し、認証自体によるログインやkeychain解錠は行いません。
- capability.serviceは既存の共通consent controllerで、送信元Process/image、セッション、操作内容、実行ファイル・引数、期限を保持します。保護された表示と新しい物理入力を確認してからパスワードを検証し、一度だけ継続処理を実行します。取消・失敗・期限切れ・送信元変更では破棄し、再利用できる昇格tokenは返しません。
- GUIはsecure-uiのViewKit認証ウィンドウ、mshの`sudo <command> [args...]`はTerminalの保護された認証欄を使います。端末の認証中はPTYへ入力を渡さず、パスワードを標準入力から読まないため、パイプへの自動応答で承認できません。認証バッファは使用後に消去します。
- Settingsのアカウント作成・削除・パスワード変更と自動ログイン設定は、この共通経路で承認された操作をbrokerが実行します。一般アプリ自体へUID 0を付与しません。アカウント作成後の初期設定に失敗した場合は、UIDの再利用へホームを渡さないよう、作成したアカウントを保持します。
- sudoは承認前に実行ファイルを捕捉し、署名・manifestと依存ライブラリのhashを確認します。承認後に同じパスの別ELFを読み直しません。独立した子プロセスだけをUID 0にし、標準I/Oと終了コードを引き継ぎます。環境変数を制限し、nativeのデバイス権限や`capabilities.manage`は付与しません。共有ライブラリは署名された依存宣言が必要です。
- パッケージ変更も共通認証に接続しました。AppStoreとmpkは同じクライアントを使い、承認前に入力MPKGと対象versionを固定します。変更直前にpackage.serviceが送信元・セッション・期限に結び付いた同じnative transaction objectの承認をbrokerで一度だけ消費します。旧式・versionedのパスだけの変更RPCは拒否します。固定コピーの親directoryと既存package管理領域はroot所有・mode・symlinkを検査します。承認待ちの間はpackage.serviceをブロックしないため、既存のCapability index更新と相互待ちしません。
- 子の資格情報設定は既存のPOSIX root launcherに対する汎用的なuserspaceの拡張です。kernelへサービス名、管理者認証、sudo専用の処理を追加していません。

user.service、capability.service、posix.service、secure-ui、Terminal、Settings、sudoに加え、package.service、AppStore、mpkと共通クライアントをmochiOSターゲットでコンパイル確認済みです。試験追加・実行、実アカウントの変更、KVM動作確認は行っていません。
