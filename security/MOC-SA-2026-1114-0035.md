## 問題と影響

`HandleWaitMany`は、待機対象の`KernelObject`を強参照として保持する`Vec<WaitSource>`を
待機中のカーネルフレームに所有させます。スレッドを終了させる処理は、そのフレームを
再開・解放することなくカーネルスタックを回収し、ローカル変数のデストラクターを実行しません。
スレッド終了時の明示的な後始末にも、このVecと保持したオブジェクトの解放はありません。

streamの読み取り側がこの経路で残ると、プロセスのHandle表と書き込み側を回収しても
読み取り側の`OpenFile`は最終解放されません。`PIPE_TABLE`のreader数が残り、
そのstreamの枠は再利用されません。通常アプリが自分の資源だけを使って起こせます。

全体のstream表は64枠で、待機対象も最大64件です。128個のHandleで64組を作り、
読み取り側を1本の待機スレッドに保持させた後、別の自スレッドからプロセスを終了すると、
その64枠が残留する経路があります。ほかの主体の既存streamの内容を読み取る問題ではなく、
以後のstream作成を全体で失敗させるサービス拒否です。
単に起動中のアプリが枠を占有する場合と異なり、原因プロセスの終了でも回復しません。

## 到達条件と根拠

- `core/src/syscall/handle.rs::stream_pair_create`は、追加Capabilityなしで自分の
  streamを作成します。`core/src/syscall/task.rs::thread_create`にも、
  自プロセスの追加スレッドを作るための追加Capability要求はありません。
- `core/src/syscall/fs.rs`は`MAX_PIPES = 64`のグローバル表を使います。
  `close_pipe_endpoint_from_kernel`が枠を空ける条件は、readerとwriterの両方が0になることです。
- `core/src/task/fd_table.rs`では、`FileHandle`が`Arc<SpinLock<OpenFile>>`を保持し、
  reader/writer数の減算は`OpenFile::drop`で行います。
- `core/src/syscall/handle.rs`の`WaitSource::Object(KernelObject)`は強参照です。
  `wait_many`は呼び出し元の表から得た対象を`WaitSource::capture`で`sources`へ格納し、
  `sleep_thread_unless_woken`と`yield_now`をまたいで保持します。
  `HANDLE_WAIT_MANY_MAX_ITEMS`は64、`PROCESS_MAX_OBJECT_HANDLES`は4096です。
- 自分で作った空のstreamを、writerを開いたままREADABLE待機することで、このスレッドを
  実際の待機状態へ進められます。他プロセスの協力や悪意あるproviderは不要です。
- `core/src/task/scheduler.rs::exit_current_process`は、終了処理で兄弟スレッドを先に
  `retire_process_threads`で破棄します。`terminate_thread`および同処理の回収経路は、
  停止済みのスレッドを`remove_thread`し、`free_kernel_stack`でstackを回収します。
  待機中のRust関数への復帰や、そのローカル所有物のDropは行いません。
- `core/src/task/thread.rs::clear_thread_wait_registrations`は、IPC lifetime、
  address wait、deadline、process exit waiter、未公開Handleの予約を後始末します。
  待機フレームの`sources`やその中のstream強参照は、この処理から到達できません。
  `ObjectWaitRegistrations::drop`もフレームが捨てられる場合は実行されません。
- その後のプロセス表の回収は通常のHandleを解放しますが、失われた強参照を減算しません。
  最終`OpenFile::drop`が起きないため、stream枠が残ります。

## 修正方針

中断され得るカーネル処理の所有物を、破棄されるスタックのRAIIだけに任せないようにします。
待機中の対象参照・購読・確保済みバッファを、スレッドの終了処理が到達できる汎用の
待機所有状態へ移し、通常復帰と終了時キャンセルのどちらでも一度だけ回収します。

参照の破棄が別のロックやIPC後始末へ入る場合は、スレッド表・プロセス表のロックを
解放してから実行します。実行中CPUとstack切替の完了を確認する既存の仕組みは維持します。
同様に強参照を保持してparkするstream読み書き・IPC・provider待機も、所有権を個別に確認します。
任意のカーネルスタックを無理にunwindすることは修正方針に含めません。

## 確認の限界

待機対象の強参照の取得、待機、兄弟スレッドの破棄、通常Handleの回収、
stream表の最終解放条件を静的に追跡しました。64枠を埋める試験や起動確認は行っていません。
通常復帰した待機は本件の残留条件ではありません。すべての種類のカーネルオブジェクトが
同じ影響を受けると確認したものでもありません。

## 同日追補：読み取り中の終了によるprovider I/O gateの残留

同じスタック破棄が、共有されるI/O gateの所有権にも影響することを確認しました。
資源の解放がローカル変数のDropだけに依存する同じ原因として、このIDで扱います。

- `core/src/syscall/handle.rs::provider_read`は、memory identityを持つproviderについて
  `lock_provider_io`で`ProviderIoGuard`を取得し、そのスコープ内で
  `provider_read_chunk`を呼びます。読み取りHandleにはREADがあれば到達できます。
- `core/src/mem/vm_object.rs::lock_provider_io`は、endpointのthread・slot・generationと
  memory identityで特定される共有の`IoLock`を取得します。同じbackingの別Handleも
  このgateを使います。gateは特定のクライアントのHandle番号に限定されません。
- `core/src/mem/object_io.rs`の`IoLock::try_lock`は`admission.locked = true`にし、
  `IoGuard::drop`だけが同フラグを解除して待機者を通知します。
- 読み取り中のprovider IPCは`core/src/syscall/ipc.rs`の
  `call_endpoint_with_attachments_from_kernel`で返信待ちになり、
  `sleep_thread_unless_woken`と`yield_now`でparkします。この時点でも外側の
  `ProviderIoGuard`は生存しています。
- 自分の別スレッドから終了させ、parkしたスレッドを破棄すると、前述の終了処理は
  このguardへ到達しません。guardの強参照と`locked = true`が残り、
  providerが後から正常に返信しても、破棄された呼び出しフレームは再開しません。

条件は、同一backingをほかの主体も利用しており、読み取りのIPCが実際に待機している間に
クライアントを終了させることです。悪意あるproviderや元ファイルへのWRITE権限は必要ありません。
以後、同じgateを取得する読み書き・同期などは進行できなくなります。
既存の常駐ページへのアクセスを含め、すべてのファイル操作が止まると主張するものではありません。

修正時はオブジェクトの強参照だけでなく、実行中操作のgate所有権も終了時の管理対象にします。
すでに発行した書き込み等がある経路では、所有者消滅を理由に盲目的にunlock・再実行せず、
処理結果不明の状態を含めて整合性を保つ必要があります。この追加経路も静的確認のみです。

## 修正と確認（2026-11-14）

core `158e9c1`で、待機対象・購読・バッファを保有する汎用の
`task::operation::Scope`を追加しました。所有allocationはスレッドに置き、
実行フレームは送信不能な借用だけを持ちます。通常復帰時と最終スレッド回収時の
両方で、スレッドキューのロックを解放してから所有物を破棄します。

`syscall/handle/wait.rs::ObjectWaitState`は対象参照、購読、配列、guard登録をまとめて
保有します。providerのI/O guardとgateの待機中参照も同じ管理対象にしています。
core `85d08ae`ではスレッド削除をスケジューラ内部のunsafe APIに限定し、
実行CPUの離脱と再開しない終了経路を呼び出し条件として明示しました。

core `d2cb483`では通常のstream/provider読み書きとstream専用読み書きについても、
対象の強参照をこのスレッド所有状態から借用するよう変更しました。
stream書き込み時に待機をまたぐ一時バッファも同様に保持します。
stream状態と最終参照の解放処理は`task/stream.rs`へ分離しています。

ホストでは実際の`task/operation.rs`を使用し、通常のDropと、スタック破棄を模した
ローカルScopeの破棄省略後の所有者回収について、キューロック外で一度だけ
デストラクターが実行されることを確認しました。既存のobject待機チェックでは
部分的な購読失敗、deadline、upcall、Handle再利用時の後始末を確認しました。
カーネルのコンパイルも通過しています。

KVM・実機での64枠枯渇と、providerが要求を実行中の強制終了は未検証です。
本記録の修正確認範囲は上記の参照・gate所有権であり、実行済みの外部I/Oを
取り消したことや、すべてのカーネルスタック上の所有物を検査し終えたことを
保証するものではありません。
